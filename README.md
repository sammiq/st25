# Star Trek: 25th Anniversary (CD, DOS) decompilation

Matching decompilation of `STARTREK.EXE`, the DOS executable from the CD release. The aim is C source that compiles to the original machine code with the original compiler. Progress is measured, and functions are compared, with [objdiff](https://github.com/encounter/objdiff).

The away-mission rooms' scripts are machine code too, but they live in the game's data files rather than the EXE. They are decompiled to assembly source separately: see [Room scripts](#room-scripts-rdf).

## The original build

| | |
|---|---|
| Compiler | Microsoft C 6.00A (`tools/C600`) |
| Memory model | Medium (`/AM`): far code, near data. Each `.C` file has its own `NAME_TEXT` segment |
| Game code flags | `/AM /G2 /qc /Gs`: 286 instructions, quick compile, no stack checks |
| Runtime | `MLIBCR` + `MLIBFP` + `EM` (8087 emulator), plus `LIBH` helpers |

These flags are what the first matched functions need. Quick-compile (`/qc`) code is easy to spot: every function starts `enter n,0 / push si / push di`, and conditionals compile to `jcc short` over `jmp near`.

## Setup

You need Python 3.11+, ninja, [emu2](https://github.com/dmsc/emu2) on `PATH`, and a Rust toolchain (to build objdiff and exepack).

```sh
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
tools/objdiff/build.sh             # patched objdiff + objdiff-cli -> tools/bin
tools/exepack/build.sh             # exepack -> tools/bin
.venv/bin/python configure.py      # writes build.ninja and objdiff.json
ninja                              # split targets, build everything
ninja progress                     # progress summary
```

These inputs are not in git, so supply your own copies:
- `orig/CD/TREKCD/STARTREK.EXE` (the original EXE, as shipped; `configure.py` checks it against `config/orig.sha1`, or run `sha1sum -c config/orig.sha1`)
- `tools/C600/` (the Microsoft C 6.00A installation: `BIN`, `INCLUDE`, `LIB`)
- `tools/MASM50/` (the Microsoft Assembler 5.0 installation: `BIN`, `INC`)

The original was linked with `/EXEPACK`, so it is compressed. The build unpacks it with David Fifield's [exepack](https://www.bamsoftware.com/software/exepack/) (`exepack -d`) into `build/exe/STARTREK.EXE`, which is the image every tool reads, and IDA too. Set `$EXEPACK` to use an exepack other than `tools/bin/exepack` or the one on `PATH`.

Open `objdiff.json` in `tools/bin/objdiff` (the GUI) for the interactive diff. It rebuilds base objects as you save.

### Rebuilding the EXE

`STARTREK.MAK` is an NMAKE makefile that rebuilds the whole program with the original tools. It compiles the C units with CL, assembles the assembly modules with MASM, combines the runtime into `MLIBCE.LIB` the way C 6.00 SETUP does, and links with LINK 5.10. `tools/dosbuild.py` runs it in DOSBox (dosbox-staging, headless) and compares the result with the shipped EXE:

```sh
.venv/bin/python tools/dosbuild.py      # -> build/dos/STARTREK.EXE, .MAP, NMAKE.LOG
.venv/bin/python tools/dosbuild.py /A   # rebuild everything
```

emu2 can't run this build: NMAKE needs a command processor, and LINK 5.10 goes wrong under emu2 with this many objects.

The original was linked with `/EXEPACK`, and so is the rebuild. The two packed files are compared directly, then both are unpacked with exepack and compared again, where each difference stays at the address it affects.

The link options are `/NOI /NOD /NONULLSDOSSEG /EXEPACK /ST:0xF00`. Without `/NONULLSDOSSEG`, LINK puts 16 zero bytes at the start of `_TEXT`. Modules link in segment order, seg000 to seg036. `asm/t35052` opens `_TEXT` (`.CODE _TEXT`), and the C runtime follows it. `asm/t3715C`, `asm/t3A200` and `asm/t41E20` aren't linked, because they are library code that LINK pulls in itself. seg006 is compiled with `/Zi`: its reference to `__aDBused` is what brings in the runtime's `dbscrswp`.

`src/BSS.ASM`, generated by `tools/genbss.py` from `symbols.txt`, comes last. LINK lays communals (uninitialized globals) out in an order of its own that depends on the original, lost variable names. So BSS.ASM defines each one as a public at its original address, in `c_common` and `FAR_BSS`, sized to the next symbol so that unreferenced variables keep their space. The C files' tentative definitions resolve to these publics. The publics must carry DGROUP (`ASSUME DS:DGROUP`), because the C objects' references take their frame from the public. BSS.ASM also declares the runtime's `XOB`/`XO`/`XOE` and `EMULATOR_DATA`, which keeps the segment order. It's a reproduction aid, not recovered source; regenerate it after renaming or resizing a `.bss` symbol.

#### Status: done

The rebuilt program image (all code and data) is identical to the original, and so are both EXE headers. The rebuilt EXE runs and plays in DOSBox. Two discrepancies remain, and the project accepts both as they are:

- **Relocation order.** The relocation table has the same 4,797 entries as the original, but 26 of them are in a different order. LINK writes them in the order it processes modules, so the original fed it some modules in a different order (one example: a relocation in seg028 comes before t35052's). DOS applies every relocation when it loads the program, whatever their order, so the program in memory is the same byte for byte.
- **`.bss` layout from `BSS.ASM`.** The uninitialized globals sit at their original addresses only because `BSS.ASM` pins them there. The original's layout came from LINK's own placement of the communals, which depends on variable names that are lost. The data starts out zeroed either way, so the program doesn't depend on how the layout was produced.

Neither affects how the game runs.

## Layout

```
config/ida_export.txt   IDA database export (tools/ida/export.idc)
config/symbols.txt      every function/data symbol: address, kind, size, name
config/units.txt        units (translation units) and their address ranges
src/<unit>.c            decompiled source, one file per unit
src/rdf/<room>.asm      room scripts, one file per .RDF (config/rdf.txt lists them)
include/                shared headers
tools/                  build tooling (below)
build/target/           target objects split from the EXE (generated)
build/base/             objects compiled from src/ or taken from the C library
```

Addresses are IDA linear addresses, so `seg000:0018` is `10018`. The load module sits at paragraph `0x1000`.

### Units

Units are generated by `tools/init_config.py`:

- **`segNNN`**: one per game code segment, which is one per original `.C` file. Rename a unit once you know its original file name. Names must be DOS 8.3 compatible, because the compiler runs under DOS.
- **`lib/<module>`**: C runtime modules found in the EXE. Their base objects come straight from the library, so they count as complete.
- **`asm/tXXXXX`**: parts of `_TEXT` that aren't library code (probably game assembly modules).
- **`far/segNNN`, `data/dXXXXX`, `data/stack`**: far data segments, and the parts of DGROUP not yet assigned to a unit.

### Symbols

`config/symbols.txt` holds linker names, so C functions and variables carry a leading underscore. IDA's placeholder names become `_sub_10018`, `_word_4B464` and so on, which lets C code use `sub_10018` as is. Rename a symbol by editing its line here (or in IDA, then re-export and re-run `tools/init_config.py`, which keeps your existing non-placeholder names). Names and addresses must be unique: the tools look symbols up both ways, so loading `symbols.txt` stops with an error that lists any repeats. Two functions that IDA named alike need distinct names (`LoadMenu` in seg014, `LoadGameMenu` in seg019).

## Room scripts (.RDF)

Each away-mission room has a `.RDF` file in `DATA.001` (53 rooms: `DEMON0`–`VENG8`). Besides the room's header (`Rdf` in `include/room.h`: depth scaling, exits, entry positions), polygons and strings, it holds the room's scripts, which are 16-bit x86 code. `LoadRoom` loads the file whole and `CallScript` calls into it with `SI` = `&room` (the `RoomState`), and the scripts call back through the far pointer at offset 0 (`ScriptService` in `src/seg008.c`). The scripts were written in assembly, not C: strings sit inline with `jmp` over them, arguments are pushed in two different styles, the helpers take arguments in registers, and some bodies run into the next script's header.

The rooms' scripts are disassembled too: each room is MASM 5.0 source in `src/rdf/<room>.asm` that assembles to the original file byte for byte (`ninja rdf`), with every script, variable and object named and commented. [docs/decompilation.md](docs/decompilation.md#room-scripts-rdf) describes the file format, the script interface and the tooling (`tools/rdf.py`).

### Quirks of the original

The scripts are hand-written and contain some oddities and outright bugs. Each source lists its own at the top. Across the rooms:

- In most rooms the last script's `next` is the helpers' code, which the engine then reads as one more script. Its "key" and "next" are instruction bytes, and the bogus `next` is past `scripts_end`, so the search stops. VENG2 is larger than that bogus `next`, so its search carries on through the middle of its code and reads two more fake scripts. One of them has the key `FF 1E 00 00`, which `RunWildScripts` matches against any message about object 1Eh.
- FEATHER3, FEATHER5 and VENG3 have scripts that run on into the next script's header, or jump to it, and execute its six bytes as code.
- DEMON1 pushes the three arguments that four `Anim` calls share before choosing between them; the fourth case pops them (`pop ax` three times) and pushes its own. One script there pushes a call's arguments and drops them again, a call that was taken out.
- The TRIAL rooms, SINS3 and VENG2 build some conversations at run time in `talk_buf` and go on through a jump table (`choice_jumps`) that the script fills in with the code for each choice.
- TRIAL2 skips a block with a `jmp`, and SINS1 has code after a `retf`. Both are dead code (`code=` in `config/rdf.txt`).
- DEMON4's conversation with the Nauian tests a flag that nothing sets, so its own "join the Federation" ending is never reached; the same lines play when the Nauian turns the key.
- In LOVE0, the script for getting door 8 has no body: its entry is the next script's header, whose six bytes run as code before its `jmp`. The doors' own answer is left unreachable behind it.
- The LOVE rooms' communicator scripts have four cases, all playing the same placeholder lines recorded for other missions. LOVE3 tests a flag nothing sets (so the insulation can always be taken). LOVE4 awards the water's point every time, because it sets the flag to 2 but tests it against 1. In LOVE5, two scripts share the key for phasers on Preax, so the second never runs.
- Two MUDD scripts have mangled keys that can never match. MUDD2's McCoy-tricorder-on-Mudd script is keyed `45h, 8, 0, 0` instead of `MSG_USE, IT_MTRICOR, 8, 0`. MUDD3's use-the-screen script has its two objects swapped. Also in MUDD2, using a bed once McCoy is ready walks Kirk with a message nothing handles. In MUDD5, firing the alien device marks it used without the +5 that every other MUDD room gives.
- FEATHER6 has two scripts keyed `MSG_USE, IT_ROCK, ANY`, so the second never runs. FEATHER5 gives Kirk McCoy's line "Jim! Are you out of your mind?".
- SINS0, SINS1 and SINS4 each have a second script with the same key as an earlier one (talking to Mosher, talking to Spock, Spock on the lock), which never runs. SINS3 has a script keyed on using object 20h, which is no item. SINS5 tests five point-once flags it never sets, so those points come every time.
- Both of VENG2's conversation menus end in a debug line from a speaker "wes" ("kirk dialog error.", "power allocation error.") for a choice that can't happen. VENG8's script for Kije reaching the transporter pad also answers a walk that is never started, and counts arrivals as if two crewmen were walking there.
